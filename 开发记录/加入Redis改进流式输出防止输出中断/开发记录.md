## 二、核心架构：Redis Stream 解耦流式输出

### 2.1 架构演进

**之前（耦合，有缺陷）**：

```
HTTP 请求 → Agent async generator 直接 yield → FastAPI SSE → Frontend
客户端刷新断开 → generator 被 Cancel → Agent 停止 → 回复丢失 ❌
```

**现在（解耦）**：

```
HTTP 请求 → 启动后台 Agent Task → 逐个事件 XADD 到 Redis Stream
HTTP 请求 → SSE 从 Redis Stream XREAD → 转发给前端
客户端刷新断开 → SSE 连接关闭，但 Agent 后台任务继续运行 ✅
客户端重连 → SSE 从上次位置继续 XREAD ✅
```

```python
class StreamManager:
```

```python
async def _read_stream_sse(conversation_id, last_event_id="0"):
    while True:

            {key: last_id}, count=50, block=60000)   # 阻塞读取
        for entry_id, fields in entries[0][1]:
            last_id = entry_id
            data = json.loads(fields["data"])
            yield f"data: {data}\n\n"
            if data.get("type") == "done":
                return
```

### 2.6 ⚠️ 关键坑：socket_timeout 与 XREAD BLOCK 冲突

**症状**：流式输出无响应，日志出现 `Stream read error: Timeout reading from 127.0.0.1:6379`

**根因**：`socket_timeout=2s` 小于 `XREAD BLOCK 60000`（60秒）。阻塞式读取每次只等 2 秒就被 socket 超时打断，SSE 读取器立即退出，前端收不到任何事件。

**修复**：

```python
socket_timeout=65,   # 必须大于 XREAD BLOCK 时长(60s)，否则阻塞读被提前打断
```

**教训**：使用 Redis 阻塞命令（BLPOP/XREAD BLOCK）时，客户端 socket_timeout 必须大于阻塞时长，否则阻塞失效。

### 2.7 断线重连机制

前端 `lastStreamEventId` 记录最后收到的事件 ID（存入 `sessionStorage` 跨刷新保留），重连时传给后端：

```
Frontend: GET /agent/active/{id}        → Redis Stream 是否存在
          GET /agent/reconnect/{id}?lastEventId=xxx  → 从该位置继续读取
```

前端关键点：
- `processStreamData()` 中读取 `data._stream_event_id`，存入 `sessionStorage`
- `checkAndReconnectStream()` 用 `isReconnecting` 标志防止无限循环（reconnect → selectChat → reconnect）
- reconnect 完成后用 `Object.assign(existing, dbMsg)` 更新已渲染消息，**不重建消息列表**（保留流式渲染效果）

## 三、功能一：消息编辑 + 重新生成 + 分支切换

### 3.1 数据库树形结构设计

`ai_session` 表新增字段：

```sql
ALTER TABLE ai_session
  ADD COLUMN parent_id BIGINT NULL,              -- 父消息ID（链表）
  ADD COLUMN branch_order INT NOT NULL DEFAULT 1, -- 同一父下分支顺序
  ADD COLUMN is_active_branch BOOLEAN NOT NULL DEFAULT TRUE,
  ADD COLUMN original_message_id BIGINT NULL;     -- 分支来源消息

ALTER TABLE conversations
  ADD COLUMN active_head_id BIGINT NULL;          -- 激活分支最新消息ID
```

> **根节点约定**：`parent_id = NULL` 表示第一条消息（根节点）。**不得**混用 `0`，否则 `get_sibling_branches` 查询 `parent_id == 0` 时找不到 `parent_id == NULL` 的原消息，分支切换失效。

### 3.2 三种操作语义

| 操作 | 行为 |
|------|------|
| **编辑+分支重新回复** | 创建新分支（`parent_id` 指向原消息的 `parent_id`），保持原消息不变，切换到新分支 |
| **编辑+不分支重新回复** | 直接 UPDATE 原消息 `question`，删除之后所有子消息，同一记录重新生成 |
| **重新生成** | **不创建分支**，复用同一 ai_session 记录，清空旧 answer 后重新跑 agent |

- **Repository**：`app/repositories/message_tree_repo.py`（新建）

## 四、关键 Bug 修复

### 4.1 Vue v-if/v-else 链错误（消息重复显示）

**症状**：发送消息后，出现"被 UI 包裹的用户输入 + 未被包裹的裸文字"重复。

**根因**：`ai-message` 用 `v-else`，但在它前面插入了编辑表单的 `v-if`，导致 `v-else` 错误关联到编辑表单，而非 `v-if="msg.role === 'user'"`。

**修复**：改为独立条件 `v-if="msg.role !== 'user'"`，断开错误链。

### 4.2 雪花 ID 精度丢失

**症状**：所有消息 ID 在 JS 中变成同一个值 `2030594695312511000`。

**根因**：MySQL 雪花 ID（~2e18）超过 JS `MAX_SAFE_INTEGER`（~9e15）。

**修复**：后端 `str(s.id)` 序列化 → Schema 用 `str` 类型 → 前端不 `parseInt` → Repo `_to_int()` 转回。

### 4.3 客户端临时 ID（chat_xxx）导致编辑失败

**症状**：`POST /branches/.../edit` 报 `消息不存在: chat_xxx`。

**根因**：`sendMessage` 用 `generateId()` 生成 `chat_xxx` 临时 ID，从不刷新获取后端数据库 ID。

**修复**：`submitEdit`/`regenerateMessage` 检测到 `chat_xxx` 时先刷新消息列表拿到真实 ID 再操作。

### 4.4 `active_head_id` 未更新

**修复**：`_save_question` 保存消息后，同步 `UPDATE conversations SET active_head_id = saved.id`。

### 4.5 Vue 响应式代理丢失（流式内容不渲染）

**症状**：`submitEdit` 后流式内容不刷新 DOM。

**根因**：`chat.messages.push(aiMsg)` 后 Vue 数组里存的是**代理对象**，而 `processStreamData(d, aiMsg)` 更新的是**原始对象**。

**修复**：push/splice 后重新获取代理引用：

```javascript
chat.messages.push(aiMsg);
const reactiveAiMsg = chat.messages[chat.messages.length - 1]; // ✅ Vue 代理
processStreamData(JSON.parse(d), reactiveAiMsg);
```

### 4.6 Redis 旧 task key 阻塞新任务

**症状**：`Conversation xxx already running on instance xxx`，新消息卡住无响应。

**根因**：服务器重启后旧实例的 Redis 锁 key（30分钟 TTL）残留。

**修复**：`task_manager.start()` 启动时清理所有 `agent:task:*` key。

## 八、遗留问题 / 下一步

1. **Redis 环境**：开发机 Redis 需 7.x（Stream 支持）。旧实例偶发卡死导致连接超时，已重启解决；如程序化解决，可在 `StreamManager.start()` 增加重试/健康检查
2. **后台任务清理**：`_background_tasks` 无上限，极端长会话建议补充任务数上限或超时清理
3. **多实例支持**：当前 `_background_tasks` 是单进程内存态；如需多实例部署，Agent 后台任务需改为独立的 worker 进程（Agent 写 Redis Stream，SSE 读 Redis Stream 已在 API 层解耦，天然支持）
4. **task_manager 分布式锁**：与 Redis Stream 共存，需确保 `stop_task` 在 agent 异常中断时可靠执行
